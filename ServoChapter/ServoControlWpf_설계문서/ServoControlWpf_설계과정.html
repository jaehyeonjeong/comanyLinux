0. 한 장 요약

이 프로젝트는 한마디로 Windows 프로그램(WPF)으로 Raspberry Pi 에 붙은 서보 모터(카메라를 좌우로 돌리는 팬)를 움직이고, Pi 모니터와 Windows 화면 양쪽에서 카메라 영상과 "서보가 언제 몇 도로 움직였는지" 기록을 보는 것입니다.
무엇설명
서보가 움직이는 원리서보는 20 ms 마다 오는 펄스의 길이로 각도를 받습니다. 1500 µs = 0°, 10 µs 마다 1°(HS-311). 펄스는 Pi 의 pigpiod 프로그램이 만들고, 우리 프로그램은 "GPIO18 을 1700 µs 로" 라는 16바이트 명령을 TCP(포트 8888)로 보낼 뿐입니다.
프로그램 3개① ServoControlWpf(Windows) — 다이얼·슬라이더로 조종, 카메라 화면, 설정. ② pi_display(Pi, Python) — Pi 모니터에 카메라 영상 + 서보 이동 로그, 영상을 HTTP 로 내보냄. ③ 에뮬레이터(가짜 pigpiod, Windows·리눅스 판) — Pi 없이 전부 시험.
연결하는 세 가지 길직접: Windows → LAN → 실제 Pi 의 8888 (Pi 가 PC 주소를 허용해야 함. 127.0.0.1 같은 자기 주소는 거부). WSL 터널: Windows → WSL 의 ssh → Pi (Pi 설정 불필요, 키 인증 필요, 무선에 권장). 에뮬레이터: 가짜 Pi — 종류를 고름: 앱 안 가짜 Pi 또는 WSL 가짜 Pi(앱이 WSL 에 fake_pigpiod.py 를 띄움). 어느 길이든 그 뒤는 같은 명령입니다.
켜는 순서① Pi: 서보 외부 5 V, pigpiod 켜짐. ② WPF 실행(Windows 에서 dotnet run 또는 WSL 에서 ./run-from-wsl.sh). ③ 연결 방식 고르고 [연결] → 화면이 서보의 현재 각도(GPW)로 맞춰짐. ④ [0°] → 조금씩 움직임 → 끝나면 [출력 끄기]. 창을 닫으면 설정과 마지막 각도가 저장됩니다.
Pi 없이 연습연결 방식 "에뮬레이터" → 종류 앱 안 가짜 Pi(가장 쉬움) 또는 WSL 가짜 Pi(명령이 가상 네트워크를 실제로 건너감, 앱이 WSL 에 fake_pigpiod.py 를 띄움) → [연결]. Pi 화면 프로그램까지 보려면 WSL 에서 python3 pi_display/pi_display.py --no-gui --fake-camera 를 함께 띄움.

2. 출발점 — 서보·Pi 기초와 통신 규약

쉬운 풀이 프로그램을 만들기 전에 정해져 있던 것은 셋입니다: 서보가 펄스 길이로 움직인다는 것, Pi 의 pigpiod 가 16바이트 명령으로 그 펄스를 만든다는 것, PC 와 Pi 가 이더넷(192.168.10.x)으로 연결돼 있다는 것. 서보 사양과 Pi 핀 배치는 데이터시트 PDF 에서 가져왔습니다.

서보 사양서(HS-311), Raspberry Pi 4B 데이터시트, 그리고 Pi 쪽 준비 스크립트(pi_setup.sh·pi_info.sh, 지금은 tools\pi)가 출발 재료였습니다.

2-1. 서보는 어떻게 움직이나 (쉬운 설명)

RC 서보는 "얼마나 긴 전기 신호를 받았느냐" 로 자기 팔(혼)을 어디에 둘지 정합니다. 20 ms(1초에 50번) 마다 짧은 High 펄스가 오는데, 그 펄스의 길이가 각도입니다.

비유 서보는 "같은 말을 계속 들어야 그 자리를 지키는" 장치입니다. 펄스를 끊으면(0) 힘을 빼고 손으로 돌릴 수 있게 됩니다. 그래서 프로그램에는 항상 [출력 끄기] 버튼이 있고, 종료할 때도 꼭 0 을 보냅니다.

핵심 사실 세 가지.

  • 통신 규약: TCP 8888, 요청·응답 모두 16바이트, 쓰는 명령은 SERVO(8)·HWVER(17)·PIGPV(26)·GPW(84) 네 개.

  • 안전 규칙: 범위 밖 각도는 잘라서 출력, 통신 끊기면 자동 해제, 종료 시 항상 펄스 0. [연결 해제] 는 옵션에 따라 출력을 유지할 수 있고(위치 기억), 연결할 때는 장치가 지금 내보내는 펄스를 읽어 화면을 맞춘다(10-10).

4. 세 가지 연결 길 — 직접(실제 Pi) · WSL 터널 · 에뮬레이터(앱 안 / WSL 가짜 Pi)

쉬운 풀이 직접은 가장 단순하지만 Pi 가 PC 주소를 허용해야 하고 실제 Pi 의 LAN 주소에만 씁니다. 터널은 WSL 의 ssh 가 길을 뚫어 주어 Pi 설정이 필요 없지만 비밀번호 없는 키 인증이 필요합니다. 에뮬레이터는 Pi 가 없을 때 가짜 Pi 를 쓰는데, 가짜 Pi 를 앱 안에 둘지 WSL 안(리눅스 프로세스)에 둘지 종류를 고릅니다. 세 길 모두 끝에서는 같은 16바이트 명령이 pigpiod 에 닿습니다.

4-1. ① 직접 연결 — 실제 Pi 전용, 왜 Pi 설정을 바꾸지 않아도 되나

직접 연결은 실제 Pi 의 LAN 주소에만 씁니다. Pi 주소 칸에 127.0.0.1·localhost·::1·0.0.0.0 을 넣고 [연결] 하면 "직접 연결은 실제 Pi(LAN 주소, 예 192.168.10.2 또는 172.30.1.81)에만 씁니다 … 가짜 Pi 로 연습하려면 연결 방식을 '에뮬레이터' 로" 라는 안내와 함께 거부합니다(MainViewModel.IsLoopbackHost). 자기 자신에게 "직접 연결" 한다는 것은 결국 같은 PC 의 가짜 서버에 붙는 것, 즉 에뮬레이션이기 때문입니다(4-5 절). 호스트 이름(raspberrypi.local)은 그대로 통과합니다.

WSL2 는 기본적으로 NAT 방식이라 WSL 안에서 보낸 패킷은 Windows 의 주소(192.168.10.1)로 바뀌어 나갑니다. 즉 Pi 의 pigpiod 는 지금까지도 "192.168.10.1 에서 온 접속" 을 받고 있었습니다. Windows 에서 직접 접속해도 Pi 가 보기에는 똑같은 주소이므로, pi_setup.sh 가 허용해 둔 목록을 그대로 씁니다.

4-2. ② WSL 터널 — "WSL 을 거쳐서" 를 글자 그대로

앱이 실행하는 명령은 이것입니다.

wsl.exe [-d 배포판] -e ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -o ConnectTimeout=5 \
        -L 127.0.0.1:18888:127.0.0.1:8888 rpi
옵션뜻 (쉽게)
-N원격에서 명령을 실행하지 않고 "통로" 만 연다
-L 127.0.0.1:18888:127.0.0.1:8888내 쪽 18888 로 들어온 것을 저쪽(Pi) 의 8888 로 보낸다
-o BatchMode=yes비밀번호나 "yes/no" 질문을 하지 않는다 (창이 없으니 물어봐도 답할 수 없음 → 키 인증 필수)
-o ExitOnForwardFailure=yes포트를 못 열면 바로 종료 → 앱이 실패를 빨리 알 수 있음

앱은 터널을 띄운 뒤 127.0.0.1:18888 이 열릴 때까지 최대 10초 기다리고, 그 다음부터는 ①과 똑같은 RemotePigpioDriver 로 접속합니다. 이미 누가 18888 을 열어 두었다면(앱이 비정상 종료돼 ssh 가 남은 경우) 새로 띄우지 않고 그대로 씁니다. 연결 해제·종료 시 Process.Kill(entireProcessTree) 로 wsl.exe 와 그 안의 ssh 를 함께 닫습니다.

4-3. ③ 에뮬레이터 — 하드웨어 없이 "진짜 경로" 를 시험

Pi 가 없을 때 그냥 화면만 움직이는 "시뮬레이션" 은 통신 코드를 전혀 검사하지 못합니다. 그래서 진짜 pigpiod 처럼 대답하는 가짜 서버를 만들었습니다.

  • 같은 16바이트 규약으로 응답. SERVO 는 펄스 범위(0, 500~2500)와 GPIO 번호를 검사해 진짜처럼 −7, −2 오류를 돌려줌.
  • HWVER → 0xc03111(Pi 4B), PIGPV → 79 를 돌려주므로 연결 바에 "Pi 리비전 c03111 · pigpio v79" 가 뜸.
  • 서보의 물리 움직임도 흉내: 목표 각도를 향해 0.19 s/60°(HS-311 @4.8 V) 속도로 움직이는 "현재 각도" 를 계산.
  • 앱은 에뮬레이터 모드에서도 ①과 완전히 같은 RemotePigpioDriver 를 쓴다. 다른 점은 접속 주소가 127.0.0.1 이라는 것뿐.

6. 데이터 흐름 — 슬라이더를 움직이면 일어나는 일

쉬운 풀이 다이얼을 돌리면 ViewModel → Model → 드라이버 → TCP → pigpiod 순서로 명령이 가고, 성공했을 때만 모델이 새 각도를 기억합니다. 그 뒤 "바뀌었다" 는 알림(Changed)으로 다이얼·각도 줄·펄스 줄·카메라 그림이 모두 같은 값으로 맞춰집니다. 실패하면 아무것도 바뀌지 않고 오류 창만 뜹니다.

다이얼을 돌렸을 때 일어나는 7단계입니다. 번호를 따라가 보세요.

  1. MainWindow: 슬라이더 값이 바뀜 → 바인딩이 MainViewModel.Angle 에 값을 넣음
  2. MainViewModel.Angle setter: 스윕 중이면 멈추고 _model.SetAngle(angle)
  3. ServoModel.SetAngle: 범위로 자른 뒤 ServoSpec.AngleToPulse() 로 펄스 계산 → driver.WritePulse(µs)
  4. RemotePigpioDriver → PigpioClient: SERVO(8, 18, µs) 16바이트 전송 → 응답 res 확인
  5. pigpiod (또는 가짜 pigpiod): GPIO18 펄스 폭 변경 → 서보 이동
  6. ServoModel: 성공하면 각도 저장 후 Changed 이벤트
  7. MainViewModel.SyncFromModel: _syncing = true 상태로 Angle·Pulse·IsOutputOn 등 PropertyChanged → 다이얼·각도 줄·펄스 줄 갱신, 왼쪽 카메라 뷰는 (연결된 상태라면) 새 목표를 향해 서보 속도로 회전 시작. 연결 해제 상태면 카메라 뷰는 움직이지 않음
무한 루프 막기 7번에서 슬라이더 값을 다시 넣을 때, 슬라이더는 또 "값이 바뀌었다" 고 ViewModel 에 알립니다. 그냥 두면 "갱신 → 요청 → 갱신 → …" 이 반복됩니다. _syncing 플래그가 켜져 있으면 Angle setter 가 값만 저장하고 명령을 보내지 않습니다.

6-1. 펄스폭으로 조작하면

펄스 줄(슬라이더·입력칸)을 바꾸면 ViewModel 의 PulseInput setter 가 받습니다. 사양 범위(최소~최대 펄스)로 자른 뒤 ServoSpec.PulseToAngle() 로 각도를 구해 위 2번부터 같은 길을 갑니다. 즉 모델이 기억하는 것은 언제나 "각도" 하나이고, 펄스폭은 사양으로 계산한 값입니다. 그래서 7번 갱신 때 각도 줄·다이얼·카메라 뷰·펄스 줄이 모두 같은 상태를 보여 주고, 보정값을 바꾸면 펄스 줄의 범위와 값도 함께 바뀝니다.

6-2. 실패했을 때

4번에서 실패하면 ServoException 이 올라옵니다. LinkLost 가 true(연결 끊김·시간 초과) 이면 ViewModel 이 먼저 연결을 정리(시뮬레이션 드라이버로 교체, 이전 드라이버가 재접속해 0 전송) 하고 오류 창을 띄웁니다. pigpio 가 거부한 오류(−7 등) 는 연결을 유지한 채 메시지만 보여 줍니다. 어느 경우든 Model 의 각도는 바뀌지 않으므로 화면이 "실제 서보 상태" 와 어긋나지 않습니다.

pigpiod 는 TCP 8888 로 명령을 받습니다. 요청과 응답은 모두 4바이트 정수 4개(리틀엔디언 = 낮은 바이트가 먼저) 입니다.

PIGPV26— / —연결 직후 pigpio 버전 읽기
예) "GPIO18 을 1500 µs 로"   →  08 00 00 00 · 12 00 00 00 · dc 05 00 00 · 00 00 00 00
    (8 = SERVO, 18 = 0x12, 1500 = 0x05dc)
C# 에서는  BinaryPrimitives.WriteUInt32LittleEndian(req[0..4], cmd)  처럼 넣는다.

이 바이트 열이 정확히 나가는지는 자동 테스트 Servo_SendsExactly16BytesLittleEndian 이 가짜 서버로 받아서 확인합니다. 오류 코드는 한글로 바꿔 보여 줍니다: −2 "사용할 수 없는 GPIO 번호", −7 "펄스폭은 0 또는 500~2500 µs", −41 "권한 없음".

8. WSL 접근 — WPF 가 리눅스를 부르는 법

쉬운 풀이 WPF 는 wsl.exe 를 자식 프로그램으로 띄워 리눅스 명령(스크립트, ssh)을 대신 실행하고 그 출력을 로그 창에 보여 줍니다. 함정 두 가지: wsl -l 같은 관리 명령은 글자 인코딩이 다르고(UTF-16), sudo 비밀번호가 필요한 스크립트는 보이는 터미널 창에서 열어야 합니다.

Windows 프로그램이 WSL 을 쓰는 가장 확실한 방법은 wsl.exe 를 실행하는 것입니다. WPF 앱은 다음 네 가지 모양으로 부릅니다.

9-1. 다이얼은 어떻게 만들었나

WPF 에는 기본 다이얼 컨트롤이 없습니다. 처음에는 슬라이더로 대신했지만 "다이얼 조종" 이라는 이름과 맞지 않아, FrameworkElement 를 상속해 직접 그리는 노브를 만들었습니다.

  • 그리기: 값 범위(최소~최대)를 화면 각도 −135°~+135°(270°) 에 비례로 펼친다. 바깥에 1° 눈금과 10° 숫자, 안쪽에 0° 부터 현재 값까지 파란 호, 가운데에 노브와 포인터, 노브 안에 각도 숫자.
  • 조작: 노브를 누르거나 끌면 중심에서 본 마우스 방향각을 atan2 로 구해 값으로 바꾼다(1° 단위로 맞춤). 아래쪽 빈 90° 구간을 가리키면 가까운 끝으로. 휠 1칸 = 1°, 포커스가 있으면 ←/→ 1°, PgUp/PgDn 10°, Home/End 끝.
  • 연결: Value 가 양방향 바인딩이라 ViewModel.Angle 과 바로 묶인다. 모델이 바뀌면 다이얼이 따라 돌고, 다이얼을 돌리면 6장의 흐름대로 서보 명령이 나간다.
  • 검증: "마우스 위치 → 값" 계산은 단위 테스트 10개로, 실제 조작은 UI 자동화(RangeValue 패턴·마우스 메시지)로 확인.

9-2. 왼쪽 화면 — 서보에 올려진 카메라의 움직임

처음에는 왼쪽에 반원 "미터기" 게이지를 두고 드래그로도 조종하게 했지만, 조종은 다이얼 하나로 충분하고 왼쪽은 "지금 모터가 실제로 어떻게 움직이는가" 를 보여 주는 편이 직관적이라 바꿨습니다. 이 프로젝트의 서보는 카메라를 좌우로 돌리는(팬) 용도이므로, 위에서 내려다본 서보 본체 위에 카메라를 올린 그림을 그립니다.

  • 표시 전용: IsHitTestVisible = false 로 마우스를 전혀 받지 않습니다. 눌러도 각도가 바뀌지 않습니다(자동 테스트로 확인).
  • 실제 속도로 움직임: 바인딩된 Angle 은 "명령한 목표" 이고, 그림의 카메라는 그 목표를 향해 HS-311 속도(0.19 s/60° ≈ 316 °/s)로 회전합니다. 그래서 −40° → +40° 명령을 주면 약 0.25 초 동안 돌아가는 모습이 보이고, 글자에 "→ 목표 +40.0° 로 회전 중" 이 표시됩니다.
  • 시야(FOV): 카메라 앞으로 62°(Pi 카메라 모듈 v2 수평 시야) 쐐기를 반투명하게 그려, 카메라가 어디를 보고 있는지 알 수 있습니다.
  • 상태 표현: 출력이 꺼지면 카메라가 회색이 되고 시야가 사라집니다(힘이 빠진 상태). 허용 범위는 연한 파란 호, 범위 끝에 닿아 있으면 "끝단 — '지잉' 소리가 나면 범위를 줄이세요" 경고가 뜹니다.
  • Model 과의 관계: 애니메이션은 화면 안에서만 일어납니다. Model 의 각도(= 서보에 보낸 명령)는 즉시 바뀌고, 그림만 뒤따라갑니다. 에뮬레이터도 같은 속도로 "현재 각도" 를 흉내 내므로 둘이 거의 일치합니다.
  • 연결됐을 때만 움직임: IsConnected 가 바인딩되어 있어, 연결 해제 상태에서는 다이얼·각도·펄스를 아무리 바꿔도 카메라는 제자리입니다. 그림은 반투명 막으로 흐려지고 "연결 안 됨 — Pi 또는 에뮬레이터에 [연결]하면 카메라 움직임이 여기에 표시됩니다" 안내만 보입니다. 이유는 단순합니다. 연결이 없으면 서보로 명령이 나가지 않으므로 실제 모터도 움직이지 않는데, 화면이 움직이면 "지금 모터가 돌고 있다" 는 거짓 정보가 됩니다. 구동 조건은 연결됨 AND 출력 켜짐 하나로 묶었고(IsDriven), 연결 직후 출력이 꺼진 상태에서는 회색 카메라가 마지막 위치에 머물다가 첫 명령으로 출력이 켜질 때 목표를 향해 출발합니다. 연결을 끊으면 회전 중이던 카메라도 그 자리에서 멈춥니다(실제 서보도 힘이 빠지면 그 자리에 머묾).

9-3. 왼쪽 위 — 실제 카메라 영상

서보에 올린 카메라가 "실제로 무엇을 보고 있는가" 를 같은 창에서 보고 싶다는 요청으로, 왼쪽을 위·아래로 나눠 위에는 실제 카메라 영상, 아래에는 9-2 의 서보 그림을 두었습니다. 아직 Pi 에 카메라가 없으므로 지금은 노트북 내장 카메라로 동작을 확인하고, 나중에 Pi 카메라를 같은 자리에 붙입니다.

  • 장치 선택 콤보박스: 프로그램을 켜면 Windows 의 카메라 장치 목록을 읽어 넣고, 저장된 장치(없으면 첫 번째 = 보통 노트북 카메라)를 자동으로 켭니다. 마지막에 "꺼짐" 항목이 있고, [정지]/[시작]·[새로 고침] 버튼, 해상도·fps 표시, 상태 줄이 있습니다.
  • 외부 패키지 없이: Windows 10 내장 API(WinRT MediaCapture + MediaFrameReader)를 씁니다. 이를 위해 앱의 대상 프레임워크를 net8.0-windows10.0.19041.0 으로 올렸고(출력 폴더 이름이 바뀜), 데스크톱 앱 카메라 권한(Windows 설정 > 개인 정보 및 보안 > 카메라)이 필요합니다.
  • 영상 경로: 카메라 → BGRA8 프레임(백그라운드 스레드) → UI 스레드로 넘겨 WriteableBitmap 한 장을 계속 덮어씀 → Image 에 바인딩. 화면이 바쁘면 프레임을 건너뛰어 밀리지 않게 합니다(1280×720 에서 약 17 fps).
  • 규격으로 분리: 영상 장치는 ICameraSource(목록·시작·정지·프레임 이벤트) 뒤에 숨겨 두었습니다. 구현은 웹캠(WinRtCameraSource)과 Pi 네트워크 카메라(MjpegCameraSource)를 CompositeCameraSource 로 하나처럼 묶은 것이라(9-4) 화면·뷰모델은 소스가 둘인지 모릅니다. 테스트는 가짜 FakeCameraSource 로 뷰모델 동작(기본 장치 선택, 저장된 장치 우선, 장치 없음 안내, 꺼짐 전환, 오류 표시, 프레임 → 비트맵)을 검사합니다.
  • 오류 처리: 권한이 없으면 설정 경로를 안내하고, 다른 프로그램이 카메라를 쓰고 있으면 그 가능성을 알려 주며, 어떤 경우에도 앱은 계속 동작합니다. 종료 때 카메라 정리는 스레드 풀에서 최대 3초만 기다립니다(UI 스레드에서 동기로 기다리면 교착되는 문제를 겪고 고침 — 18장).

9-4. 카메라 목록의 "Pi 카메라 (네트워크)"

같은 콤보박스에 Pi 의 pi_display 가 내보내는 MJPEG 스트림이 한 항목으로 들어갑니다. 고르면 URL 줄이 나타나고(비우면 "Pi 주소:8889" 로 자동), 영상은 웹캠과 똑같은 자리에 같은 방식으로 그려집니다. 구조상 CompositeCameraSource 가 웹캠(WinRtCameraSource)과 네트워크(MjpegCameraSource)를 하나의 목록으로 합쳐 CameraViewModel 에 넘기므로, 뷰모델·화면은 소스가 둘인지 모릅니다. 웹캠 권한이 없어도 Pi 항목은 보입니다. 상세는 15장.

9-5. 긴 글이 잘리지 않게 — 글꼴 자동 축소

쉬운 풀이 "가짜 Pi 수신: ✓ SERVO gpio=18 1750 µs → 목표 +25.0°" 같은 글은 길이가 매번 달라서 자리를 넘치면 끝이 잘렸습니다. 이제 그런 자리는 공간이 모자라면 글꼴을 조금씩 줄이고(기준 15pt → 최소 10~11pt), 그래도 모자라면 "…" 으로 자르되 마우스를 올리면 전체 글이 툴팁으로 보입니다. 창을 좁혀도 버튼이 밀려 사라지지 않도록 긴 글은 연결 바 아래 전용 줄로 옮겼습니다.
  • 어디에: 연결 정보 줄(장치 이름·Pi 리비전·가짜 Pi 수신), 상태 바, 카메라 화면 상태("Integrated Camera · 영상 수신 중"), 다이얼 아래 출력 상태. 왼쪽 서보 그림의 상태 글(위치 유지 중·회전 중·끝단 경고·연결 안 됨)도 그림 폭에 맞춰 글꼴을 줄입니다.
  • 어떻게: View\ShrinkTextBlock — TextBlock 하나를 품은 작은 컨트롤. WPF 가 Measure 때 넘겨주는 "쓸 수 있는 폭"(MaxWidth 가 있으면 그것)을 예산으로 삼아, 글의 자연 폭(FormattedText)이 예산보다 크면 글꼴을 비례로 줄입니다. TextBlock 을 그대로 상속하지 않은 이유는 그 Measure 가 봉인되어 있고, 잘려 그려져도 ActualWidth 는 글 전체 폭을 보고하기 때문입니다(18장).
  • 배치: 연결 바는 조작 요소만(연결 방식·종류·주소/포트·[연결]·[전체화면]·[종료]) 두어 창 최소 폭 1120 에서도 다 보이고, 정보 줄은 ● + 장치 이름(최대 380px) + Pi 리비전(최대 320px) + 가짜 Pi 수신(남는 폭 전부)로 나눠 각자 예산 안에서 줄어듭니다.

10. 운용 원리와 기법

쉬운 풀이 쓰는 순서는 "전원 → 연결 → 0° → 조금씩 → 출력 끄기". 연결하면 프로그램이 서보의 지금 상태(GPW)를 읽어 화면을 맞추고, 끊거나 끌 때도 위치를 기억해 다음에 이어집니다. 끝단에서 "지잉" 소리가 나면 범위를 줄이세요. 무선으로 쓰려면 10-11 절(터널 모드 권장).

이 장은 "프로그램을 어떻게 돌리고, 왜 그렇게 해야 하는가" 를 다룹니다. 처음 운용하는 사람은 10-6 절차와 10-7 안전 수칙만 먼저 읽어도 됩니다.

10-1. 서보 제어의 원리 — 펄스 폭이 곧 각도

  • 프레임: 20 ms 마다 한 번(50 Hz). 이 주기는 거의 모든 아날로그 서보의 약속입니다.
  • 폭: HS-311 은 1500 µs 가 0°, ±400 µs 가 ±40°. 즉 10 µs = 1°. 프로그램의 AngleToPulse 가 이 비례식을 계산합니다(중립 기준으로 + 쪽, − 쪽 따로).
  • 데드밴드 5 µs: 펄스가 5 µs 이내로 바뀌면 서보가 움직이지 않습니다. 0.5° 미만 변화는 의미가 없다는 뜻이므로, 프로그램은 1° 단위 조작을 기본으로 둡니다.
  • 위치 유지: 같은 펄스를 계속 받으면 서보는 외부 힘에 저항하며 그 자리를 지킵니다(이때 전류가 흐릅니다). 펄스 0 이면 힘을 뺍니다.
  • 속도: 0.19 s/60°(4.8 V). 80° 를 가려면 약 0.25 초. 스윕 속도를 200 °/s 넘게 올려도 서보가 따라오지 못합니다(최대 약 315 °/s).

10-2. 왜 pigpiod 인가 — "한 번 말하면 계속 해 주는" 데몬

리눅스 프로그램이 GPIO 를 직접 켰다 껐다 하면 운영체제의 다른 작업 때문에 타이밍이 흔들려 서보가 떨립니다. pigpiod 는 Pi 의 DMA 하드웨어로 펄스를 만들기 때문에 µs 단위로 정확하고, 한 번 "GPIO18 에 1500 µs" 라고 하면 다음 명령이 올 때까지 스스로 계속 내보냅니다.

운용에 미치는 뜻
  • 프로그램은 각도가 바뀔 때만 명령을 보내면 됩니다. 네트워크가 잠깐 느려져도 서보는 마지막 위치를 지킵니다.
  • 반대로 접속이 끊겨도 펄스는 계속 나갑니다. 그래서 프로그램은 끊긴 뒤에도 0.5 초 재접속을 시도해 0 을 보내고, 종료 때도 꼭 0 을 보냅니다. 비정상 종료 후 서보가 계속 힘을 주고 있으면 Pi 에서 pigs s 18 0 으로 끌 수 있습니다.

10-4. SSH 터널 기법 — 준비와 점검

  1. WSL 터미널에서 ssh rpi 가 비밀번호 없이 들어가는지 확인합니다. 안 되면 ssh-keygen 후 ssh-copy-id rpi.
  2. ~/.ssh/config 에 별명이 있어야 합니다: 
    Host rpi
    HostName 192.168.10.2
    User user
  3. 손으로 터널을 시험하려면: ssh -N -L 127.0.0.1:18888:127.0.0.1:8888 rpi 를 한 창에서 띄우고, WPF 를 "에뮬레이터 · WSL 가짜 Pi · Pi 포트 18888" 로 접속합니다(포트가 이미 열려 있으면 새로 띄우지 않고 그 포트에 붙으므로 터널 끝의 실제 pigpiod 에 닿음).
  4. 앱은 18888 이 이미 열려 있으면 재사용합니다. 남은 터널을 지우려면 WSL 에서 pkill -f "ssh -N".
  5. ssh 가 바로 죽으면 앱 오류 창에 ssh 의 stderr(예: "Host key verification failed") 가 그대로 표시됩니다. 그 문장으로 원인을 찾습니다.

10-5. 보정 기법 — 내 서보에 맞추기

서보는 개체마다 중립과 끝단이 조금씩 다릅니다. 보정은 "중립 → 끝단 → 저장" 순서입니다.

  1. 중립 맞추기: [0°] 를 누르고 혼이 원하는 중앙을 가리키는지 봅니다. 어긋나면 "중립 펄스" 를 10 µs 씩 바꿔 [적용]. (10 µs = 1°)
  2. 끝단 찾기: 공식값(±40°) 에서 시작해 [최대 ▶] 로 보낸 뒤, 필요하면 "최대 펄스" 를 20 µs 씩 올리며 [적용]. '지잉' 소리가 계속 나면 기계적 한계에 닿은 것 — 바로 20~30 µs 줄입니다. 최소 쪽도 같은 방법.
  3. 각도 표시 맞추기: 끝단 펄스에 해당하는 실제 각도를 각도기로 재서 "최대 각도/최소 각도" 에 넣으면 화면 각도가 실제와 일치합니다. + 쪽과 − 쪽 기울기가 달라도 프로그램이 따로 계산합니다.
  4. 저장: [적용] 하면 자동 저장됩니다(%APPDATA%\VI\ServoControl.json). [공식값 ±40°] 로 언제든 되돌릴 수 있습니다.
확장값 ±90° 는 "시험용" 600~2400 µs 는 제조사 보증 범위 밖입니다. 끝단에서 기어가 걸리면 스톨 전류(최대 800 mA)가 흐르고 레진 기어가 상할 수 있습니다. 프로그램이 확인 창을 띄우는 이유입니다.

10-7. 안전 운용 수칙

  • 전원: 서보는 외부 5 V 2 A 이상. Pi 의 5 V 핀으로 돌리면 전압이 떨어져 Pi 가 재부팅되거나 SD 카드가 손상될 수 있습니다.
  • GND 공통: 묶지 않으면 신호가 인식되지 않거나 서보가 떨립니다.
  • 신호 3.3 V: Pi GPIO 는 3.3 V 입니다. 대부분의 아날로그 서보가 인식하지만, 안 움직이면 레벨 변환기를 씁니다. 서보 쪽 5 V 를 GPIO 에 넣으면 안 됩니다.
  • 한쪽에서만 조종: Pi 쪽 도구(pigs 등)와 WPF 가 동시에 명령하면 마지막 명령이 이깁니다. 헷갈리니 한쪽만 씁니다. (pi_display 는 읽기만 하므로 괜찮음)
  • 힘을 빼 두기: 위치를 유지할 필요가 없으면 출력을 끕니다. 부하가 걸린 채 오래 유지하면 발열·전류가 큽니다.
  • 끝단 소리: '지잉' 이 계속 나면 즉시 반대쪽으로 움직이거나 출력을 끄고 범위를 줄입니다.

10-11. 무선(Wi-Fi) 으로 연결할 때 — WSL 과 Pi 설정

프로그램은 TCP 주소만 알면 되므로 이더넷(192.168.10.x)에 묶여 있지 않습니다. 무선으로 바꿀 때 달라지는 것은 두 가지뿐입니다: ① Pi 가 Wi-Fi 에 붙어 IP 를 갖는다, ② pigpiod 의 허용 주소(-n)가 PC 의 Wi-Fi IP 와 맞아야 한다(직접 연결) — 또는 ssh 터널로 우회한다(WSL 터널). 공유기가 주는 IP 는 바뀔 수 있으므로 무선에서는 WSL 터널 모드를 권합니다(Pi 쪽 설정이 전혀 없고, PC IP 가 바뀌어도 됨).

10-12. 에뮬레이션이 안 될 때 — 포트 8888 을 누가 쓰고 있나

쉬운 풀이 "앱 안 가짜 Pi" 는 127.0.0.1:8888 을 들어야 하는데, 같은 PC 에서 이미 누군가 8888 을 듣고 있으면 같은 자리에 앉을 수 없습니다. 특히 WSL 에서 fake_pigpiod.py 를 띄워 두면 WSL2 가 그 포트를 Windows 의 127.0.0.1 로도 열어 줍니다(wslrelay.exe). 앱은 빈 포트를 골라 자동으로 피하고 알려 주며, 그 WSL 가짜 Pi 에 붙고 싶으면 종류를 "WSL 가짜 Pi" 로 바꾸면 됩니다.
상황보이는 것해결
WSL 에서 fake_pigpiod.py/pigpio-emu 가 8888 을 듣는 중연결은 되고 상단에 "가짜 Pi 대기 중: 127.0.0.1:임시 포트 (포트 8888 은 다른 프로그램이 사용 중)", 상태 줄에 안내그대로 써도 됨. 그 가짜 Pi 에 붙고 싶으면 에뮬레이터 종류를 "WSL 가짜 Pi" 로(이미 열린 포트를 재사용). 끄려면 WSL 에서 pkill -f '[f]ake_pigpiod.py'

13-1. WSL 셸에서 실행하기 — "통신만으로" 띄우고 연결하기

프로그램 폴더를 WSL 의 리눅스 파일시스템(\\wsl.localhost\Ubuntu\home\jhjung\MyJob\projects\comanyLinux\ServoChapter\ServoControlWpf)에 두고, WSL 터미널에서 명령만으로 실행하고 연결할 수 있는지 이 PC 에서 확인했습니다 (실제 Pi 는 연결되어 있지 않음).

원리 — WPF 는 리눅스에서 돌지 않지만, WSL 은 Windows 프로그램을 "대신 띄워" 준다 WSL 의 interop 기능 덕분에 리눅스 셸에서 .exe 를 실행하면 Windows 가 그 프로그램을 띄웁니다. 창은 Windows 화면에 뜨고, 네트워크·설정 파일(%APPDATA%)도 Windows 쪽을 씁니다. 즉 "WSL 에서 실행" 은 Windows 프로그램을 WSL 터미널에서 원격 조종하듯 띄우는 것이고, 그 뒤의 연결(직접·터널·에뮬레이터)은 Windows 에서 띄웠을 때와 완전히 같습니다. 리눅스용 .NET 을 설치해도 WPF 는 실행되지 않습니다.
WSL 셸에서 띄우는 방법결과비고
A. ./ServoControlWpf.exe 직접 실행 (리눅스 FS 의 .exe)✔Windows 에서 복사해 넣은 파일은 실행 비트가 없어 "Permission denied" → chmod +x 한 번 필요. Windows 는 이 파일을 \\wsl.localhost\… 경로로 읽어 실행
B. dotnet.exe "$(wslpath -w …/ServoControlWpf.dll)"✔실행 비트 불필요. 경로는 wslpath -w 로 Windows 형식(UNC)으로 바꿔 줘야 함 (리눅스 경로를 주면 "예상 원인" 오류)
C. powershell.exe Start-Process△WSL 셸이 돌아오지 않고 멈추는 경우가 있어 권장하지 않음
D. cmd.exe /c start "" "\\wsl.localhost\…"✗cmd 는 UNC 경로를 지원하지 않음
E. 리눅스 dotnet run --project ServoControlWpf✗WPF 는 Windows 전용 (net8.0-windows). 리눅스 .NET 은 NETSDK1100("Windows 대상 프로젝트는 이 OS 에서 빌드할 수 없다") 오류를 냄. Directory.Build.targets 가 이 상황을 미리 감지해 "./run-from-wsl.sh build 를 쓰세요" 라는 한글 안내로 바꿔 줌
F. 리눅스 dotnet run --project PigpioEmulatorCli -- 8888 0.0.0.0✔가짜 pigpiod(pigpio-emu)는 WPF 를 쓰지 않는 보통 콘솔 프로그램이라 리눅스 .NET 10 에서도 돌아감(RollForward). D 의 python 판 fakepi 와 같은 역할
리눅스 dotnet 설치 중 겪은 문제와 결론 WSL 에 snap install dotnet 으로 넣은 .NET 10 은 libunwind8 라이브러리가 없어 dotnet --version 부터 실패했고, Ubuntu 26.04 의 apt 저장소에는 dotnet-sdk-8.0 이 없어 dotnet-sdk-10.0 을 설치해야 했습니다. 설치가 끝난 뒤에도 WPF 는 위 E 처럼 빌드되지 않습니다. 결론: 리눅스 dotnet 은 이 프로그램을 쓰는 데 필요하지 않습니다. 15-2. 왜 "서보 이동 로그" 를 pigpiod 를 읽어서 만드나

WPF 가 "내가 20° 로 보냈다" 고 Pi 에 알려 주는 방식도 가능하지만, 그러면 다른 도구(pigs, 스크립트)가 움직인 것은 빠집니다. 대신 Pi 프로그램이 pigpiod 에 50 ms 마다 GPW(84) 로 "지금 펄스폭" 을 물어 바뀔 때만 기록합니다. 누가 움직였든 서보가 실제로 받은 값이고, 10-10 절의 "연결 시 GPW 로 화면 맞추기" 와 같은 명령이라 WPF 와 Pi 가 같은 숫자를 봅니다. 각도는 같은 공식(servo_spec.py = C# ServoSpec.PulseToAngle)으로 계산하며, 보정값이 다르면 --calib 로 맞춥니다. 누가 움직였는지는 WPF 가 UDP 8890 으로 보내는 메모("WPF +20.0° 1700us")를 1초 안의 다음 변화에 붙여 보충합니다(없어도 동작).

15-3. 카메라 백엔드 자동 강등 체인

Pi 의 카메라 스택은 OS 이미지 시기에 따라 다릅니다(libcamera 또는 레거시). 그래서 --camera auto 는 picamera2 → libcamera-vid → picamera → opencv 순으로 시도해 처음 성공한 것을 쓰고, 선택 결과를 화면 상태줄과 로그에 적습니다. --fake-camera 는 움직이는 테스트 패턴(PIL 이 없으면 내장 JPEG 2장 번갈아)이라 Pi 가 없는 PC(WSL)에서도 전체 흐름을 돌릴 수 있습니다. 어느 백엔드든 결과는 "JPEG 한 장" 이고 FrameHub 가 최신 1장만 보관하므로, 느린 클라이언트가 있어도 지연이 쌓이지 않습니다(밀린 프레임은 버림).

15-4. WPF 쪽 — 소스를 하나로 묶기

기존 CameraViewModel 은 ICameraSource 하나만 받습니다. 웹캠과 네트워크를 둘 다 넣기 위해 뷰모델을 고치지 않고 CompositeCameraSource 로 두 소스를 하나처럼 보이게 했습니다(목록 합치기, ID 가 mjpeg: 로 시작하면 네트워크, 활성 소스의 프레임만 통과). MjpegCameraSource 는 HTTP 응답 헤더까지만 기다린 뒤 스레드 풀에서 바이트를 읽고, MjpegStreamParser(순수 파서, 청크가 어디서 잘려도 동작)로 JPEG 를 꺼내 WPF 디코더로 BGRA 바이트를 만들어 기존 FrameArrived 경로로 보냅니다. 끊기면 1→5초 간격으로 다시 붙습니다.

15-5. 버전 관리

버전의 단일 진실은 VERSION 파일(예 1.1.0)입니다. Directory.Build.props 가 빌드 때 이것을 읽어 모든 프로젝트의 어셈블리 버전에 박고, 프로그램은 AppVersion 으로 꺼내 제목 표시줄과 상태 바에 보여 줍니다.
